# repair2 수리 요청 프로세스 분석 — PPT 제작 가이드
**제작 목표:** 채용담당자의 과제 평가기준을 충족하면서 문제 발견 → 근거 확인 → 개선 제안의 분석 흐름을 보여주는 발표자료
**권장 분량:** 16:9 가로 슬라이드 10장 | **기준 자료:** `repair2_분석_수정검증.ipynb`, `repair2.csv` | **작성 기준일:** 2026-10-26

## 1. 제작 원칙
- B안의 스토리 중심으로 구성하되 과제 평가기준을 빠짐없이 대응
- 3페이지 전체 프로세스 구조와 5페이지 시간 비중 프로세스 흐름도를 구분해서 배치
- 차트 제목은 분석 항목보다 발견된 사실을 표현  숫자 아래에는 반드시 분석 대상과 단위를 표시
- 시간 분석은 339건  업무 구조 분석은 1,000건  업무별 처리 시간은 유효하게 연결된 3,151쌍 기준
- 1970년 날짜는 정확성이 검증되지 않아 모든 시간 수치는 탐색적인 기록상 경과 시간으로 표기
- 연관성은 인과관계와 구분  긴 대기 시간은 곧바로 불필요한 병목 또는 절감 가능한 시간으로 해석하지 않음
- 문장 안의 쉼표는 항목 나열에만 사용  문장 끝 마침표 생략  태스크명은 원본 영문 유지

## 4. 슬라이드 상세 제작 가이드
### 01  수리 요청 프로세스 분석 및 개선 제안
- **대응 평가기준:** 과제 전체
- **슬라이드 한 문장:** 수리 요청의 처리 구조를 재구성하고 주요 대기 구간과 관련 요인을 분석해 개선 방향을 제안함
- **권장 화면 구성:** 좌측 제목과 과제 목적  우측 핵심 수치 3개를 여백 있게 배치
- **필수 수치·차트:** 히어로 지표 1,000건 / 927건 일반 경로 / 339건 시간 분석 표본
- **발표 설명:** 분석 질문 ① 어떤 흐름으로 처리되는가 ② 어디에서 오래 걸리는가 ③ 어떤 요소와 관련되는가 ④ 무엇을 개선할 것인가
- **노트북 근거:** 7-1, 8-2, 9-5
- **오해 방지:** 표지에는 70.8%를 확정된 병목 성과처럼 크게 강조하지 않음  핵심 수치는 뒤에서 근거 제시

### 02  데이터 품질을 검토하고 분석 대상을 구분하다
- **대응 평가기준:** 기본 분석 및 데이터 전처리
- **슬라이드 한 문장:** 전체 1,000건의 업무 구조는 활용하되 시간 계산은 기준을 충족한 일반 경로 339건에 한정함
- **권장 화면 구성:** 상단 데이터 규모  하단에 전체 분석과 시간 분석이 갈라지는 선별 구조
- **필수 수치·차트:** 전체 1,000건 · 13,262개 이벤트 → 업무·경로 분석 1,000건 / 날짜·시간 검토 → 1970년 기록만 있는 시각 완전 케이스 402건 → 일반 경로 339건
- **발표 설명:** 시간값 누락  연도 1905·1970·2020~2022 혼재  날짜 보정 보류  분석 대상 선정의 이유
- **노트북 근거:** 1~5, 9-1~9-5
- **오해 방지:** 1970년이 실제 업무 발생 연도라는 뜻이 아님  결측과 연도 이상을 일괄 삭제하거나 임의 보정한 것처럼 설명하지 않음

### 03  수리 요청은 일반·예외 경로와 수리 업무로 분기된다
- **대응 평가기준:** 1-1 현재 프로세스 설명
- **슬라이드 한 문장:** 전체 요청은 일반 경로 927건과 예외 안내 경로 73건으로 구분되며 일반 경로는 조사 후 수리 업무로 분기됨
- **권장 화면 구성:** 대형 전체 프로세스 흐름도  좌측 진입  중앙 일반 경로  하단 예외 분기  우측 종료
- **필수 수치·차트:** FirstContact → {일반 927 / 예외 73}  일반: MakeTicket → ArrangeSurvey → Survey → 수리 업무(InternRepair / ImmediateRepair / ExternRepair) → RepairReady → 종결 관련 업무 → TicketReady  예외: InformClientWrongPlace
- **발표 설명:** 중간 안내 업무 InformClientSurvey는 보조 노드로 표시  단일·복합·반복 수리 가능  ReadyInformClient와 SendTicketToFinAdmin은 단정적 고정 순서로 연결하지 않음
- **노트북 근거:** 8-2, 10-3~10-5
- **오해 방지:** 이 그림은 10-5-1 경로 구분 Sankey와 달리 업무 순서의 이해를 위한 요약 도식  ExternRepair는 start만 기록되어 완료 시각 추정 금지

### 04  일부 케이스에서 복합 수리와 반복 수행이 관찰된다
- **대응 평가기준:** 1-2 반복작업 분석
- **슬라이드 한 문장:** 일반 경로 927건 중 복합 수리는 91건이며 InternRepair 반복 기록은 전체 일반 경로에서 38건 확인됨
- **권장 화면 구성:** 좌측 단일/복합 수리 구성  우측 InternRepair 반복 관찰과 시간순 예시
- **필수 수치·차트:** 단일 수리 836건 vs 복합 수리 91건  별도 카드로 InternRepair 반복 기록 38건
- **발표 설명:** 시간순 반복 기록 29건 검토 중 28건은 완료 후 다시 시작하는 형태  반복 수행과 재작업은 다름
- **노트북 근거:** 10-3-2~10-3-3, 10-5, 12-5
- **오해 방지:** 복합 수리 91건과 반복 38건은 서로 배타적 집단이 아니므로 합계 또는 하나의 구성비로 표현하지 않음

### 05  전체 처리 시간에서 조사 시작 전 대기가 가장 큰 비중을 차지한다
- **대응 평가기준:** 1-2 병목 후보 분석
- **슬라이드 한 문장:** 시간 분석 대상 339건에서 ArrangeSurvey 완료 → Survey 시작 구간은 전체 기록상 처리 시간 합계의 70.8%를 차지함
- **권장 화면 구성:** 프로세스 시간 흐름도에 구간별 시간 비중을 시각적으로 배치  70.8% 구간만 강하게 강조
- **필수 수치·차트:** FirstContact complete → ArrangeSurvey complete 1.9% → Survey start 70.8% → RepairReady complete 22.5% → TicketReady complete 4.9%
- **발표 설명:** 케이스 전체 처리 시간 중앙값 77.3시간  70.8%는 구간 시간 합계 / 전체 시간 합계  그림에 계산 기준 명시
- **노트북 근거:** 12-2-1, 12-4-1
- **오해 방지:** 각 구간 비중은 소수 첫째 자리 반올림으로 합계가 100.1%일 수 있음  절감 가능 시간이나 실제 운영 지연율로 표현하지 않음

### 06  ArrangeSurvey → Survey 대기는 다수의 케이스에서 길게 나타난다
- **대응 평가기준:** 1-2 병목 후보 상세 분석
- **슬라이드 한 문장:** 해당 대기 구간의 중앙값은 54.5시간이고 P90은 195.7시간이며 211/339건에서 24시간을 초과함
- **권장 화면 구성:** 왼쪽 0 / 0~24 / 24~72 / 72~168 / 168시간 초과 분포 차트  오른쪽 지표 카드 3개
- **필수 수치·차트:** 0시간 39건  0~24시간 89건  24~72시간 63건  72~168시간 90건  168시간 초과 58건  중앙값 54.5h · P90 195.7h · 24시간 초과 62.2%
- **발표 설명:** P90은 약 90%가 그 시간 이하에 있는 경계값이라는 설명  정상적인 조사 예약 대기와 운영 지연 구분 불가
- **노트북 근거:** 12-3-1~12-3-3
- **오해 방지:** P90을 상위 10%의 평균으로 설명하지 않음  24시간 초과는 설정한 분석 경계일 뿐 실제 SLA 위반 근거가 아님

### 07  E 유형은 실제 수리보다 수리 착수 전 대기가 상대적으로 길다
- **대응 평가기준:** 1-3 케이스 소요 시간 관련 요소
- **슬라이드 한 문장:** E 유형은 Survey 완료 이후 첫 수리 시작까지 중앙값 25.2시간을 기록하며 같은 InternRepair 업무만 수행한 집단에서도 긴 대기가 나타남
- **권장 화면 구성:** 상단 B·E·P 유형별 대기/착수 이후 시간 비교  하단 동일 업무 조건 비교
- **필수 수치·차트:** 338건 비교: B 46건 0.0h / 3.2h  E 143건 25.2h / 4.0h  P 149건 0.0h / 2.2h  순서는 수리 전 대기 / 수리 시작 이후 RepairReady까지  추가 비교 InternRepair 1:1 E 127건 대기 25.9h · 실제 업무 4.0h
- **발표 설명:** E 유형 전체 처리 시간 중앙값 160.4시간과 수리 시작 전 대기 증거를 연결  유형별 업무 구성 차이를 통제하려 한 후속 분석 설명
- **노트북 근거:** 14-1, 14-4-1, 14-4-2
- **오해 방지:** 개별 구간 중앙값끼리 합해 전체 중앙값을 만들지 않음  수리 시작 이후 경과 시간과 InternRepair 실제 start→complete 시간을 구분

### 08  Web·Letter 접수에서 ArrangeSurvey 장시간 처리 사례가 집중된다
- **대응 평가기준:** 1-3 케이스 소요 시간 관련 요소
- **슬라이드 한 문장:** ArrangeSurvey 809건 중 1시간 초과 194건이 모두 Web·Letter에서 발생하며 담당자 변경 여부와도 관련성이 관찰됨
- **권장 화면 구성:** 왼쪽 접수 채널별 1시간 초과율  오른쪽 동일/변경 처리 시간 중앙값과 주의 문구
- **필수 수치·차트:** Web 109/207 52.7%  Letter 85/175 48.6%  Phone 0/224  Personal 0/203  동일 담당자 704건 중앙값 4분  상이 담당자 105건 중앙값 332분
- **발표 설명:** Web 중앙값 119분 vs Letter 중앙값 5분  담당자 동일한 Web·Letter에서도 1시간 초과 89건  처리 시간은 ArrangeSurvey 내부 start→complete
- **노트북 근거:** 12-1-2~12-1-4, 13-3~13-4
- **오해 방지:** 시작·완료 담당자가 다르다고 실제 인수인계가 발생했다고 단정하지 않음  접수 채널과 지연의 인과관계는 미확인

### 09  확인된 문제를 기준으로 세 가지 개선 과제를 제안한다
- **대응 평가기준:** 2 프로세스 개선 방안
- **슬라이드 한 문장:** 긴 기록상 경과 시간이 확인된 구간을 우선 점검하고 원인을 추가 기록한 뒤 검증된 조건에만 개선안을 적용함
- **권장 화면 구성:** 가로 3열 카드  각 카드에 문제 → 추가 기록 → 가능한 운영 조치  오른쪽 순위 표시
- **필수 수치·차트:** 1순위 조사 예정 시각·착수 상태  2순위 E 유형 수리 예정 시각·진행 상태  3순위 Web·Letter 세부 업무 상태·담당자 변경 사유
- **발표 설명:** 확정된 원인은 아님  원인 확인 → 시범 조정 → 재측정 순서  자재 확보나 인력 부족을 원인으로 단정하지 않음
- **노트북 근거:** 15-2~15-5
- **오해 방지:** 우선순위는 검토 순서이지 확정된 절감효과 순서가 아님

### 10  추가 기록과 효과 검증으로 개선 효과를 확인한다
- **대응 평가기준:** 2 개선 방안 및 결론·한계
- **슬라이드 한 문장:** 실제 예정 시각과 상태 기록을 확보한 뒤 일정 준수와 전체 처리 시간의 개선 여부를 함께 검증해야 함
- **권장 화면 구성:** 왼쪽 핵심 검증 지표  오른쪽 데이터 한계와 최종 결론
- **필수 수치·차트:** 조사 착수 지연 시간  예정 시각 초과 미착수율  수리 시작 전 대기 시간  ArrangeSurvey 채널별 1시간 초과율  전체 처리 시간 중앙값·P90
- **발표 설명:** 개선 전후 RepairType·접수 채널을 나눠 확인  지연의 다른 구간 이동 여부 평가  새 타임스탬프로 기준선 재설정
- **노트북 근거:** 15-2~15-5, 9-4~9-5
- **오해 방지:** 1970년 연도 진위 미확인  예정 시각 미기록  ExternRepair 완료 시각 부재  개선 효과 예상 수치를 만들어 넣지 않음

## 5. 프로세스 그림 2개 제작 지침
### 5-1. 03페이지 — 전체 프로세스 구조 이해용
**그림 역할:** 업무 순서와 주요 분기 및 경로 규모를 설명
```text
                        [전체 요청 1,000건]
                                │
                         FirstContact
                     ┌──────────┴──────────┐
               일반 경로 927건         예외 경로 73건
                     │                       │
                 MakeTicket        InformClientWrongPlace
                     │
                ArrangeSurvey ── (InformClientSurvey 안내 기록)
                     │
                   Survey
                     │
          ┌──────────┼────────────┐
      InternRepair  ImmediateRepair  ExternRepair
          └──────────┼────────────┘
            단일·복합·반복 수행 가능
                     │
                 RepairReady
                     │
       ReadyInformClient / SendTicketToFinAdmin
                     │
                 TicketReady
```
- 흐름도는 설명을 위한 요약이므로 전체 케이스에 완전 동일한 순서가 존재한다는 뜻이 아님
- `ReadyInformClient`와 `SendTicketToFinAdmin`은 순서가 고정된 단일 직렬 단계로 단정하지 않음
- `InformClientSurvey`는 주요 수리 분기와 별도인 중간 안내 기록으로 작게 표시
- `ExternRepair`는 `start` 이벤트만 기록되어 업무 완료 시간을 표시하지 않음
- 일반·예외의 상호 배타적 분기 수치 927건과 73건을 정확히 표시

### 5-2. 05페이지 — 전체 처리 시간 비중 강조용
**그림 역할:** 전체 처리 시간 합계에서 긴 경과 시간이 기록된 위치를 한눈에 전달
```text
FirstContact complete
       │ 1.9%
ArrangeSurvey complete
       ║ 70.8%  ← 핵심 대기 구간
Survey start
       │ 22.5%
RepairReady complete
       │ 4.9%
TicketReady complete
```
- 각 비중은 339개 케이스에서 해당 구간 시간 합계를 전체 처리 시간 합계로 나눈 비율
- `Survey start → RepairReady complete` 22.5%에는 현장 조사 업무와 수리 관련 구간이 함께 포함됨
- 70.8% 구간만 시각적으로 강조  모든 대기가 불필요한 지연이라는 표현은 사용하지 않음
- 반올림 때문에 비중 합계가 100.1%로 표시될 수 있음

## 7. 디자인·문장·수치 품질 기준
- 화면은 16:9  상하좌우 여백 일정  한 슬라이드에 주요 차트 1개 또는 비교 차트 2개 이하
- 제목은 결과를 말하는 문장으로 작성  제목 아래에 근거가 되는 차트 배치
- 한눈에 읽히는 글자 크기 우선  권장 제목 28~32pt  본문 16~20pt  주석 10~12pt
- 색상은 기본 중립색을 사용하고 핵심 구간 70.8%와 핵심 비교만 하나의 강조색으로 표현
- 모든 그래프에 단위와 표본 수를 같이 명시  시간은 시간(h) 또는 분(min)으로 통일
- 중앙값·P90과 전체 시간 합계 비중은 서로 다른 통계량이므로 시각적으로 구분
- 시간 차이를 특정 인원 과부하 또는 자재 문제의 증거로 단정하지 않음
- P90은 전체의 약 90%가 해당 값 이하에 위치하는 경계값  상위 10%의 평균이 아님
- 15-2~15-4에서 새로 제안한 예정 시각·지연 사유는 현재 CSV에서 산출할 수 없는 신규 수집 항목
- RepairType B·E·P의 명칭이나 의미를 검증 없이 임의로 풀어 쓰지 않음
