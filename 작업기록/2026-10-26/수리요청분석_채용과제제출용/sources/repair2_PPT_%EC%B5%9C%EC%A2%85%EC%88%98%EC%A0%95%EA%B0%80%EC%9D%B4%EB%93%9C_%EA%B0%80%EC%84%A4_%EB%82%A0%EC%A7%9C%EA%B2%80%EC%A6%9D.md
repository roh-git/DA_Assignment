# 퍼즐데이터 수리 요청 프로세스 분석 PPT 수정 가이드 — 초기 가설·날짜 검증 중심

**수정 대상**  `repair2_수리요청프로세스_분석발표(2).pdf` 10장  
**권장 구성**  기존 주요 차트와 디자인을 유지하면서 12장으로 재편  
**목적**  채용담당자가 처음 읽어도 `가설 → 데이터 검증 → 탐색 → 결과에 따른 추가 분석 → 개선 제안 → 효과 검증 및 한계` 흐름을 이해할 수 있도록 수정

## 1. 이번 수정의 핵심

1. 최초 분석 목적과 초기 검토 가설을 앞부분에 배치하고 모든 가설이 사전에 확정돼 있었던 것처럼 표현하지 않음
2. 날짜 이상을 발견한 근거와 **1970년 기록을 2020년으로 바꾸지 않은 이유**를 독립 슬라이드로 설명
3. 날짜를 통째로 삭제하거나 바꾸지 않고 업무 경로 분석과 시간 분석의 **사용 표본을 나눴다는 판단**을 명시
4. 업무 처리 시간이 길다는 사실과 업무 사이 대기가 길다는 사실을 구분하고 앞선 결과가 다음 분석으로 이어지는 이유를 표시
5. 구체적인 개선안과 측정할 지표를 연결하되 확인되지 않은 지연 원인은 단정하지 않음

## 3. 신규 02페이지 — 분석 가설과 검토 질문

**페이지 제목**  수리 요청의 지연과 반복 작업이 어디에서 발생하는지 확인하고자 했다

**분석 목적 문장**  요청 처리 시간이 길어지는 원인이 특정 업무의 수행 시간인지 업무 사이의 대기인지 확인하고 반복 수행 및 수리 유형·접수 채널·담당자 기록과의 관계를 살펴보고자 함

| 초기 검토 질문 | 분석에 사용할 방법 | 주의할 점 |
|---|---|---|
| 특정 구간에서 대기 시간이 길게 나타날 수 있는가 | 업무 처리 시간과 업무 간 대기 시간 비교 | 긴 대기를 곧바로 불필요한 병목으로 단정하지 않음 |
| 같은 수리 업무가 반복되는 사례가 있는가 | 케이스별 업무 종류와 start·complete 순서 비교 | 반복 기록과 재작업을 구분 |
| 담당자나 접수 채널에 따라 처리 시간 차이가 있는가 | 담당자별 업무 분포와 ArrangeSurvey 채널별 처리 시간 비교 | 처리 건수와 업무 과부하를 동일시하지 않음 |
| 수리 유형과 업무 구성에 따라 케이스 처리 시간이 다른가 | RepairType별 전체 경과 시간 및 수리 구간 비교 | 단순 집단 차이로 인과관계 결론 불가 |

**전달하고 싶은 한 문장**  처음부터 병목 위치를 알고 시작한 것이 아니라 검토할 가설을 세운 뒤 데이터의 실제 흐름과 시간 기록을 차례로 확인함

**시각화**  '질문 4개 → 데이터 구조 및 날짜 검증 → 프로세스와 시간 분석'의 간단한 흐름도

> 이 질문들은 발표용으로 정리한 검토 가설임 분석 도중 새로 생긴 후속 질문까지 모두 사전 등록된 가설로 포장하지 않음

## 4. 신규 04페이지 — 날짜 오류 검증·보정 보류·분리 분석

**구분명**  날짜 오류 검증 및 전처리  
**메인 제목**  날짜 이상 패턴을 확인했지만 근거 없는 연도 변경은 하지 않았다

**슬라이드에서 답해야 할 질문**  `1970년으로 보이는 기록을 왜 2020년으로 바꾸지 않았는가`와 `그 결과 어떤 데이터를 분석에 사용했는가`

### A. 이상 날짜를 발견한 실제 근거

| 확인 항목 | 결과 | 의미 |
|---|---|---|
| 날짜 분포 | 1970년 12,383행 / 2020~2022년 860행 / 1905년 6행 / 날짜·시각 결측 13행 | 연도 혼재 발견 |
| 원본 행 순서 검사 | 0~859행의 날짜가 `2020-01-06`부터 `2022-05-14`까지 하루씩 증가 | 서로 다른 케이스의 날짜가 행 순서에 따라 움직이는 비정상적 패턴 |
| 시작·완료 연결 | 비교 가능한 업무 쌍 중 226건에서 완료 시각이 시작 시각보다 빠르게 기록 | 실제 사건 순서를 훼손할 수 있는 날짜 불일치 정황 |
| 복원 검토 | 2020~2022년 이벤트 일부는 같은 케이스 내 1970년 이벤트와 시각이 같았지만 서로 다른 업무 | 시각 일치만으로 원래 날짜 확정 불가 |

**발표에서 사용할 짧은 설명**

> 2020~2022년 날짜는 원본 행 순서에 따라 규칙적으로 증가했고 일부 업무에서는 시작보다 완료가 먼저 기록됐음
>
> 하지만 이 현상만으로 실제 날짜가 1970년인지 2020년인지 또는 어떤 규칙으로 잘못 바뀌었는지 확인할 수 없었음
>
> 따라서 1970년을 2020년으로 일괄 변경하지 않고 원본을 보존한 뒤 분석 목적에 따라 사용 대상을 분리함

### B. 선택할 수 있었던 방식과 실제 판단

| 처리 대안 | 판단 | 이유 |
|---|---|---|
| 1970년을 2020년으로 일괄 치환 | **선택하지 않음** | 실제 연도와 변환 규칙을 검증할 근거가 없음 |
| 다른 연도 및 이상치가 포함된 행 전부 삭제 | **선택하지 않음** | 업무 구성 및 경로 분석에 필요한 기록까지 잃게 됨 |
| **원본 유지 후 목적별 표본 분리** | **선택** | 날짜에 의존하지 않는 정보는 최대한 보존하면서 경과 시간 해석 범위를 제한 가능 |

### C. 실제로 어떻게 데이터를 나눴는가

| 분석 목적 | 사용한 대상 | 해석 범위 |
|---|---|---|
| 업무 종류와 흐름 및 반복 여부 | **전체 1,000건** | 날짜의 정확성과 무관하게 이벤트 존재 여부·업무 구성을 분석 |
| 개별 업무 수행 시간 | **3,151개 start·complete 업무 쌍** | 같은 1970년으로 기록되고 시간 역전이 없는 1:1 업무 쌍에 한정 |
| 케이스 전체 처리 시간 및 업무 간 대기 | **일반 경로 339건** | 모든 이벤트 시각이 존재하고 모두 1970년으로 기록된 케이스에 한정 |
| 참고 | 연도·시각 조건 충족 402건 중 예외 경로 63건은 일반 경로 시간 분석에서 제외 | 분석 대상의 성격을 혼동하지 않도록 분리 |

**반드시 표시할 주석**  `1970년을 실제 발생 연도로 인정했다는 의미가 아님 · 계산된 시간은 기록상 탐색 값 · 339건을 927건 전체의 대표 표본으로 단정할 수 없음`

**추천 시각화**  왼쪽은 날짜 이상 근거 2가지(연도별 건수와 행 순서에 따른 날짜 증가)  오른쪽은 `원본 유지 → 경로 1,000건 / 업무 시간 3,151쌍 / 케이스 시간 339건` 분리 흐름도

**디자인 팁**  표 3개를 모두 한 슬라이드에 넣지 말 것  슬라이드에는 핵심 숫자와 판단 흐름만 놓고 이 문서의 상세 근거는 발표자 노트와 별도 분석 보고서에 유지

## 5. 분석 결과가 다음 단계로 이어지는 설명

| 슬라이드 전환 | 앞서 확인한 결과 | 그래서 다음에 확인할 것 |
|---|---|---|
| 04 → 05 | 날짜를 임의 수정하지 않고 업무 기록을 보존 | 전체 케이스에서 업무 흐름과 분기 파악 |
| 05 → 06 | 수리 업무가 단일·복합으로 수행됨 | 동일 업무의 실제 반복 여부와 재작업 가능성 검토 |
| 06 → 07 | 반복 기록만으로 불필요한 작업이라고 판단할 수 없음 | 실제 시간이 어디에서 오래 걸리는지 비교 |
| 07 → 08 | ArrangeSurvey에서 일부 긴 수행 시간이 나타났지만 전체 지연을 충분히 설명하지 못함 | 업무 사이의 대기 시간과 전체 시간 비중 분석 |
| 08 → 09 | Survey 시작 전의 대기가 큰 비중을 차지함 | 수리 유형별 전체 처리 시간과 수리 시작 전 대기 비교 |
| 09 → 10 | E 유형의 수리 착수 전 대기가 긴 특성 관찰 | 접수 채널과 시작·완료 담당자 기록으로 추가 비교 |
| 10 → 11 | Web·Letter와 담당자 기록 차이 관찰 | 확정되지 않은 원인은 추가 기록으로 구분한 뒤 개선 제안 |
| 11 → 12 | 세 가지 개선 검토 대상 선정 | 실제 일정 준수 여부와 전체 완료 시간으로 성과 검증 |

**07페이지에 넣을 근거 예시**

- `ArrangeSurvey` 처리 시간 중앙값 4분 vs P90 404.8분
- `ArrangeSurvey` 수행 시간이 1시간을 넘는 집단과 그렇지 않은 집단의 전체 처리 시간 중앙값은 각각 약 78.2시간 vs 77.2시간
- 따라서 `ArrangeSurvey` 내부 수행 시간이 긴 사실만으로 전체 처리 시간 증가를 설명할 수 없다고 판단하고 업무 사이 대기를 살펴봄

**분석의 한계**

- 기존 1970년 날짜의 실제 정확성은 검증되지 않음
- 조사·수리 예정 시각이 없으므로 약속된 대기와 실제 지연을 구분할 수 없음
- 담당자 수와 처리 건수만으로 인력 부족이나 지연 원인을 단정할 수 없음
- `ExternRepair` 완료 시각이 없어 직접적인 업무 처리 시간 계산 불가
- 1시간·24시간 기준은 탐색 분석용 구간이며 실제 운영 SLA가 아님

## 7. 디자인과 가독성 최종 점검표

- [ ] 모든 페이지에 **분석 단계명**이 표시되어 있는가
- [ ] 표지 다음 페이지에서 **무엇을 확인하려고 분석했는지** 이해되는가
- [ ] 날짜 이상을 `발견 → 확인 → 대안 비교 → 보정 보류 → 분석 표본 분리`로 설명하는가
- [ ] **1970년을 2020년으로 바꾸지 않은 이유**를 명시하는가
- [ ] 1970년 기록을 실제 정확한 날짜라고 주장하지 않는가
- [ ] 이벤트 수와 업무 쌍 수 및 케이스 수를 구분하는가
- [ ] 도표 제목에 분석 표본과 단위를 표시하는가
- [ ] 슬라이드에는 하나의 핵심 메시지만 담는가
- [ ] 원본 영문 taskID와 한국어 업무 설명을 함께 표시하는가
- [ ] 이전 슬라이드 결과가 다음 분석의 근거로 이어지는가
- [ ] 발견된 관련성을 **원인**이라고 표현하지 않는가
- [ ] 개선 제안마다 측정 가능한 성과 지표가 있는가
- [ ] 중요 주석은 작은 출처 텍스트에만 의존하지 않는가
- [ ] 과제 요구사항(기본 분석·전처리·프로세스·문제점·영향 요소·개선안)을 모두 확인할 수 있는가
