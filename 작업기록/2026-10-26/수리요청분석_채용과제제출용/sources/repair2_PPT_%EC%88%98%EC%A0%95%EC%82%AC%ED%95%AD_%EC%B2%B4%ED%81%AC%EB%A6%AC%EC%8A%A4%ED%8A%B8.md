## 2. 페이지별 상세 수정 지침

### 07페이지 — 수리 유형과 전체 처리 시간의 관계 보완

**현재 구성**

- 수리 유형별 `Survey complete → 첫 수리 start` 대기 시간과 `첫 수리 start → RepairReady complete` 경과 시간 비교
- `InternRepair` 단독·시작/완료 1:1 연결 E 유형 127건의 대기 시간과 실제 작업 시간 제시

**수정 이유**

- 과제의 요구사항은 케이스 소요 시간과 관련된 데이터 요소를 근거와 함께 제시하는 것
- 현재 장표에는 조사 완료 이후 구간별 비교가 있지만 `RepairType`에 따른 **케이스 전체 처리 시간 차이**가 본문 차트로 드러나지 않음
- `첫 수리 start → RepairReady complete`는 순수 수리 작업 시간과 동일한 지표가 아니므로 명칭을 구분해야 함

**수정 내용**

1. `RepairType`별 전체 처리 시간 중앙값을 소형 비교 그래프 또는 요약 표로 추가

   | RepairType | 분석 대상 | 전체 처리 시간 중앙값 |
   |---|---:|---:|
   | B | 46건 | 11.6시간 |
   | E | 143건 | **160.4시간** |
   | P | 150건 | 71.4시간 |

2. 기존 구간별 그래프를 유지할 경우 왼쪽 그래프 표본 **338건**과 전체 처리 시간 비교 표본 **339건**을 분리 표기
3. `첫 수리 start → RepairReady complete`는 **수리 시작 이후 경과 시간**으로 표기하고 실제 `InternRepair start → complete` 작업 시간과 혼동하지 않도록 수정
4. 좁은 지면에서 정보가 과밀하면 전체 처리 시간 비교를 중심에 놓고 세부 구간 분석을 오른쪽 요약 영역으로 축소

**권장 핵심 문장**

> E 유형은 케이스 전체 처리 시간 중앙값이 가장 길게 나타남  
> 조사 완료 후 수리 시작 전 대기에서도 유형 간 차이가 확인되며 `InternRepair` 단독 케이스로 범위를 좁혀도 E 유형의 대기 시간이 상대적으로 길게 나타남

**해석 주의**

- `RepairType`과 소요 시간의 **관계**를 보여주는 결과이며 수리 유형이 지연을 일으킨다는 인과관계는 입증되지 않음
- 구간별 중앙값은 별도로 계산하므로 합계가 전체 처리 시간 중앙값과 일치하지 않을 수 있음

### 05페이지 — 시간 비중과 실제 프로세스 흐름 연결

**현재 구성**

- 339건의 전체 처리 시간 합계를 네 구간으로 나눠 `1.9% / 70.8% / 22.5% / 4.9%` 제시
- 70.8% 자체는 잘 강조되어 있지만 각 구간이 어느 업무의 시작과 완료를 기준으로 구성되는지 직관적으로 파악하기 어려움

**수정 내용**

1. 기존 시간 비중 막대를 **업무 경계가 표시된 가로형 흐름도**와 연결하거나 대체
2. 아래 순서를 시각적 기준으로 배치

   ```text
   FirstContact complete
           │ 1.9%
   ArrangeSurvey complete
           │ 70.8%  ← 가장 큰 기록상 대기 구간
       Survey start
           │ 22.5%
    RepairReady complete
           │ 4.9%
     TicketReady complete
   ```

3. `ArrangeSurvey complete → Survey start` 구간만 기존 청록색 강조색으로 표현
4. `70.8%`는 **339건의 구간별 경과 시간 합계에 대한 비중**이라고 표기
5. `22.5%` 구간에 `Survey`와 수리 관련 경과 시간이 함께 포함된다는 주석 유지

**권장 핵심 문장**

> 시간 분석 대상 339건의 기록상 전체 처리 시간 합계에서 `ArrangeSurvey complete → Survey start` 구간이 70.8%를 차지함

**해석 주의**

- 70.8%는 **줄일 수 있는 시간의 비율**이나 확인된 병목 손실률이 아님
- 네 구간의 비중 합이 100.1%로 보이는 것은 반올림 때문임
- 도식의 처음은 `FirstContact start`가 아니라 **`FirstContact complete`**를 기준으로 함

### 08페이지 — Web·Letter의 차이 드러내기

**현재 구성**

- Web 52.7%와 Letter 48.6%의 `ArrangeSurvey` 1시간 초과율 강조
- 시작·완료 담당자가 같은 집단과 다른 집단의 처리 시간 중앙값을 오른쪽에 비교

**수정 이유**

- 두 채널 모두 긴 처리 사례가 많지만 중앙값은 서로 다름
- 1시간 초과율만 보면 Web과 Letter의 처리 시간 분포가 비슷하다고 오해할 수 있음

**수정 내용**

1. 채널별 중앙값을 기존 초과율 차트 옆에 추가하거나 차트를 표와 결합

   | 접수 채널 | 분석 건수 | 처리 시간 중앙값 | 1시간 초과율 |
   |---|---:|---:|---:|
   | Web | 207건 | **119분** | 52.7% |
   | Letter | 175건 | 5분 | 48.6% |
   | Phone | 224건 | 3분 | 0.0% |
   | Personal | 203건 | 4분 | 0.0% |

2. 우측의 담당자 비교 **동일 704건·4분 / 서로 다름 105건·332분**은 유지
3. `Web·Letter`에서 담당자가 동일해도 1시간 초과 사례가 **89건** 발생했다는 설명 유지
4. 제목이나 결론에서 접수 채널 또는 담당자 변경을 지연의 원인으로 단정하지 않음

**권장 핵심 문장**

> Web은 처리 시간 중앙값부터 높게 나타난 반면 Letter는 중앙값이 짧아도 장시간 처리 사례가 높은 비율로 관찰됨  
> 담당자 차이 여부와 처리 시간 사이에도 관련성이 나타나지만 실제 인수인계나 지연 원인은 확인되지 않음

**해석 주의**

- `ArrangeSurvey start → complete`와 `ArrangeSurvey complete → Survey start`는 **서로 다른 분석 구간**임
- 1시간 초과는 탐색 분석용 기준이며 확인된 업무 SLA는 아님

### 03페이지 — 전체 프로세스 흐름도 연결 보완

**현재 구성**

- 1,000건에서 일반 927건과 예외 73건이 갈라지고 일반 경로에서 수리 업무가 분기되는 구조
- 전체적인 흐름은 전달되지만 예외 73건에서 `InformClientWrongPlace`로 이어지는 선이 약하거나 끊겨 보임

**수정 내용**

1. **예외 73건 → `InformClientWrongPlace`** 연결선을 명확하게 표시
2. `FirstContact`가 1건 미기록된 점은 기존 하단 주석처럼 유지
3. `InternRepair / ImmediateRepair / ExternRepair`가 반드시 한 가지로만 수행되는 구조가 아니라는 설명 유지
4. `ReadyInformClient`와 `SendTicketToFinAdmin` 사이에 고정된 순서를 임의로 부여하지 않음
5. `ExternRepair`에 `complete` 이벤트가 없다는 한계도 유지
6. 필요 시 수리 업무 전환 생키 다이어그램은 보조 자료로 활용하고 **3페이지 본문은 간결한 구조 요약 흐름도**로 유지

**권장 핵심 문장**

> 수리 요청은 일반 처리 경로와 잘못 접수된 요청의 예외 경로로 구분되며 일반 경로에서는 여러 수리 업무가 단일 또는 복합 형태로 기록됨

### 10페이지 — 효과 검증 지표 계산식 보완

**현재 구성**

- 조사 착수 지연 시간과 예정 시각 초과 미착수율 및 전체 처리 시간 측정 지표 제시

**수정 내용**

1. **조사 착수 지연 시간**은 기존 정의 유지

   `max(0, 실제 Survey 시작 시각 − 조사 예정 시각)`

   - 예정 시각보다 일찍 시작한 경우 0으로 처리

2. **예정 시각 초과 미착수율**은 백분율 계산을 명시

   `(예정 시각 초과 미착수 건수 / 예정 시각이 지난 전체 대상 건수) × 100`

   - 정해진 조회 시각을 기준으로 계산
   - 아직 조사 예정 시각이 지나지 않은 건은 분모에서 제외
   - 조회 시각 전에 이미 조사가 시작된 건은 분자에서 제외

3. 현재 로그에는 **조사 예정 시각과 수리 예정 시각이 없으므로 신규 수집 후 산출 가능한 지표**임을 명시
4. 개선 전후에는 구간 시간뿐 아니라 케이스 전체 처리 시간도 함께 비교
5. 1970년 날짜 정확성이 검증되지 않았으므로 신뢰할 수 있는 새 기록으로 기준선을 재설정한 후 검증한다는 설명 유지
