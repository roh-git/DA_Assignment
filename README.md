# 주택 수리 요청 프로세스 분석

네덜란드 임대 주택 기관의 수리 요청 기록을 바탕으로, 요청별 업무 구성과 처리 흐름을 살펴보는 데이터 분석 과제입니다. 기본 분석을 출발점으로 지연·반복 후보와 관련 특성을 확인하고, 근거가 있는 개선 방향을 제안합니다.

## 데이터

- 원본: [repair2.csv](repair2.csv)
- 규모: **13,262행 × 13개 칼럼**, 수리 요청 **1,000건**, 업무 **13종류**
- `caseID`: 수리 요청 번호 / `taskID`: 업무 이름 / `eventtype`: 시작·완료 상태
- `originator`: 담당 식별자 / `date`, `time`: 기록된 날짜와 시각
- 요청 속성: `contact`, `RepairType`, `objectKey`, `RepairInternally`, `EstimatedRepairTime`, `RepairCode`, `RepairOK`

한 행은 **업무 이벤트 기록**입니다. 같은 작업의 시작과 완료가 각각 기록될 수 있으므로, 행 수와 실제 업무 수행 횟수는 구분합니다.

### 칼럼 설명

아래 한글 명칭은 원본 칼럼명과 실제 기록값을 이해하기 위한 번역입니다. 별도 정의가 확인되지 않은 코드의 의미와 시간 단위는 확정하지 않았습니다.

| 칼럼 | 한글 명칭 | 설명 및 기록값 |
| --- | --- | --- |
| `caseID` | 수리 요청 번호 | 하나의 요청을 구분하는 식별자. 같은 요청의 여러 업무 이벤트가 같은 번호를 사용 |
| `taskID` | 업무명 | 접수·조사·수리·안내 등 13가지 업무. 아래 업무명 번역표 참고 |
| `originator` | 업무 수행 주체 | 담당자 또는 시스템 등의 식별 이름. `System`은 시스템 표기이며, 다른 이름의 개인·업체 구분은 추가 확인 필요 |
| `eventtype` | 이벤트 상태 | `start`: 시작 / `complete`: 완료. 해당 업무 이벤트의 상태이며 요청 전체의 완료 여부와는 구분 |
| `contact` | 접수 채널 | `Phone`: 전화 / `Personal`: 대면 / `Letter`: 서신 / `Web`: 웹 |
| `RepairType` | 수리 유형 코드 | `B`, `E`, `P`. 각 코드의 구체적인 의미는 미확인 |
| `objectKey` | 대상 식별 번호 | 수리 대상과 관련된 식별 키로 해석. 주택·설비 등 정확한 식별 대상은 미확인 |
| `RepairInternally` | 내부 수리 여부 | `True`: 내부 수리 / `False`: 내부 수리 아님. 결측은 미기록으로 구분 |
| `EstimatedRepairTime` | 예상 수리 시간 | 기록값: `60`, `120`, `160`, `220`, `240`, `360`, `480`. 시간 단위와 산정 범위는 미확인 |
| `RepairCode` | 수리 코드 | `1`, `2`, `3`, `4`. 코드별 의미는 미확인하며 숫자 크기를 등급으로 해석하지 않음 |
| `RepairOK` | 수리 정상 여부 | 이름상 수리 결과의 정상 여부를 나타내는 항목. 원본의 비결측값은 `True`만 존재하며 판정 기준은 미확인. 결측을 실패로 해석하지 않음 |
| `date` | 기록 날짜 | 이벤트가 기록된 날짜. 연도 혼재가 있어 시간 분석 전 검증 필요 |
| `time` | 기록 시각 | 이벤트가 기록된 시각. `date`와 결합해 분석용 `timestamp` 생성 |

### 업무명 번역 (`taskID`)

업무 이름을 기준으로 옮긴 설명이며, 표의 나열 순서는 실제 수행 순서를 의미하지 않습니다.

| 원본 업무명 | 한글 설명 |
| --- | --- |
| `FirstContact` | 최초 연락·접수 |
| `MakeTicket` | 작업 요청서 생성 |
| `ArrangeSurvey` | 조사 일정 조율 |
| `InformClientSurvey` | 고객에게 조사 안내 |
| `Survey` | 조사 수행 |
| `ImmediateRepair` | 즉시 수리 |
| `InternRepair` | 내부 수리 |
| `ExternRepair` | 외부 수리 |
| `RepairReady` | 수리 완료 처리 |
| `ReadyInformClient` | 고객에게 완료 안내 |
| `TicketReady` | 작업 요청서 완료 처리 |
| `SendTicketToFinAdmin` | 재무 행정 부서로 작업 요청서 전달 |
| `InformClientWrongPlace` | 고객에게 접수처가 맞지 않음을 안내 |

완료 관련 업무의 구체적인 종료 조건은 별도 확인이 필요합니다. 특히 `InformClientWrongPlace` 기록만으로 고객 이탈이나 수리 실패를 확정하지 않습니다.

### 수행 주체와 미기록값

- `originator`의 비결측값은 16종류입니다: `System`, `Monica`, `Edd`, `Dian`, `Anne`, `Cindy`, `John`, `Barbara`, `Nick`, `Ben`, `DoIt`, `Paul`, `Eric`, `Jacky`, `Lex`, `FixIt`.
- `System`을 제외한 고유 이름은 원문을 유지합니다. 이름만으로 역할이나 소속을 확정하지 않습니다.
- 위 표의 기록값은 결측값을 제외한 값입니다. 결측은 별도의 업무 유형이나 `False`가 아니라 **해당 이벤트에 값이 기록되지 않은 상태**로 다룹니다.
- 요청 속성은 일부 이벤트에만 기록될 수 있으므로, 이벤트 단위 결측과 케이스 전체의 미기록을 구분합니다.

## 분석 흐름

**전처리 → 기본 분석 → 처리 흐름 탐색 → 시간 데이터 검증 → 병목·관련 요인 → 개선안**

1. 결측값·자료형을 확인하고 날짜와 시간을 결합해 `timestamp`를 생성합니다.
2. 업무별 이벤트와 상태, 케이스별 기록 수·업무 종류 수·업무 조합, 접수 채널·수리 속성을 확인합니다.
3. 주요 업무 구성과 분기·종료·반복 후보를 탐색합니다. 업무 조합과 실제 처리 순서는 구분합니다.
4. 연도 혼재·동일 시각·시작과 완료 연결을 검증하고 시간 분석 범위를 정합니다.
5. 수행 시간·업무 간 간격·케이스 소요 시간을 구분하고, 담당 업무와 요청 특성별 차이를 비교합니다.
6. 확인한 사실 → 원인 가설 → 개선안 → 검증 지표를 연결해 PPT로 정리합니다.

## 현재 진행 내용

2026-10-27 저장본 기준입니다. 노트북에는 107개 코드 셀의 실행 결과가 저장되어 있으며 오류 출력은 없습니다. 저장된 결과를 확인한 것으로, 이번 변경에서 전체 코드를 다시 실행하지는 않았습니다.

| 구간 | 현재 상태 |
| --- | --- |
| 전처리·기초 탐색 (1~5, 7단계) | 자료형·결측·이벤트 구성·업무 조합·요청 속성 집계와 시각화 |
| 시작·종료 경로와 날짜 검증 (8~9단계) | 경로 후보, 연도 혼재, 시작·완료 연결 조건과 시간 분석 범위 정리 |
| 업무 흐름·반복·기록률 (10~11단계) | 주요 경로·분기·반복 후보와 프로세스 맵 작성, 기록률의 해석 한계 정리 |
| 처리 시간·대기 (12단계) | 업무 시간·전체 시간·업무 간 대기·반복 수리 집단 비교 |
| 담당자·수리 속성 (13~14단계) | 동일 업무의 담당자 기록과 채널·수리 유형별 시간 차이 비교 |
| 개선안 (15단계) | 조사 착수 전 대기, E 유형의 수리 착수 전 대기, Web·Letter 일정 조율을 검토 대상으로 선정하고 추가 기록·효과 검증 지표 제안 |

업무 구성은 전체 1,000건을 사용합니다. 개별 업무 시간은 시각 조건을 충족한 시작·완료 3,151쌍, 케이스 전체 시간은 일반 경로 927건 중 339건(36.6%)을 대상으로 합니다. 실제 발생 날짜의 정확성은 검증되지 않았으며, 시간 결과와 개선 우선순위는 탐색적으로 해석합니다.

저장소는 원본 데이터·분석 노트북·README 세 파일로 구성합니다. 분석 결과와 개선안은 노트북에서 함께 확인합니다.

## 해석 기준과 남은 검증

- 원본 `raw`와 분석용 전체 데이터 `df`를 구분합니다.
- 날짜·시간 누락 기록 13행을 보존합니다. 시간 분석에서 제외한다면 제외 행·케이스와 영향을 기록합니다.
- 1905·1970·2020\~2022년이 섞여 있습니다. 연도 차이만으로 날짜를 수정하거나 오류로 확정하지 않습니다.
- `timestamp` 변환 성공과 업무적으로 올바른 시각은 다릅니다. 시간 검증 전 소요 시간을 병목 근거로 사용하지 않습니다.
- 업무 조합은 포함된 업무 종류이며, 처리 순서나 반복 실행 횟수가 아닙니다.
- 요청 속성의 이벤트 단위 결측과 케이스 단위 미기록·상충값을 구분합니다.
- 담당자별 기록량이나 집단 간 시간 차이만으로 업무 과중·성과·지연 원인을 단정하지 않습니다.
