# 주택 수리 요청 프로세스 분석

네덜란드 임대 주택 기관의 수리 요청 기록을 바탕으로, 요청별 업무 구성과 처리 흐름을 살펴보는 데이터 분석 과제입니다. 기본 분석을 출발점으로 지연·반복 후보와 관련 특성을 확인하고, 근거가 있는 개선 방향을 제안합니다.

## 데이터

- 원본: [repair2.csv](repair2.csv)
- 규모: **13,262행 × 13개 칼럼**, 수리 요청 **1,000건**, 업무 **13종류**
- `caseID`: 수리 요청 번호 / `taskID`: 업무 이름 / `eventtype`: 시작·완료 상태
- `originator`: 담당 식별자 / `date`, `time`: 기록된 날짜와 시각
- 요청 속성: `contact`, `RepairType`, `objectKey`, `RepairInternally`, `EstimatedRepairTime`, `RepairCode`, `RepairOK`

한 행은 **업무 이벤트 기록**입니다. 같은 작업의 시작과 완료가 각각 기록될 수 있으므로, 행 수와 실제 업무 수행 횟수는 구분합니다.

## 분석 흐름

**전처리 → 기본 분석 → 처리 흐름 탐색 → 시간 데이터 검증 → 병목·관련 요인 → 개선안**

1. 결측값·자료형을 확인하고 날짜와 시간을 결합해 `timestamp`를 생성합니다.
2. 업무별 이벤트와 상태, 케이스별 기록 수·업무 종류 수·업무 조합, 접수 채널·수리 속성을 확인합니다.
3. 주요 업무 구성과 분기·종료·반복 후보를 탐색합니다. 업무 조합과 실제 처리 순서는 구분합니다.
4. 연도 혼재·동일 시각·시작과 완료 연결을 검증하고 시간 분석 범위를 정합니다.
5. 수행 시간·업무 간 간격·케이스 소요 시간을 구분하고, 담당 업무와 요청 특성별 차이를 비교합니다.
6. 확인한 사실 → 원인 가설 → 개선안 → 검증 지표를 연결해 PPT로 정리합니다.

## 해석 기준과 남은 검증

- 원본 `raw`와 분석용 전체 데이터 `df`를 구분합니다.
- 날짜·시간 누락 기록 13행을 보존합니다. 시간 분석에서 제외한다면 제외 행·케이스와 영향을 기록합니다.
- 1905·1970·2020~2022년이 섞여 있습니다. 연도 차이만으로 날짜를 수정하거나 오류로 확정하지 않습니다.
- `timestamp` 변환 성공과 업무적으로 올바른 시각은 다릅니다. 시간 검증 전 소요 시간을 병목 근거로 사용하지 않습니다.
- 업무 조합은 포함된 업무 종류이며, 처리 순서나 반복 실행 횟수가 아닙니다.
- 요청 속성의 이벤트 단위 결측과 케이스 단위 미기록·상충값을 구분합니다.
- 담당자별 기록량이나 집단 간 시간 차이만으로 업무 과중·성과·지연 원인을 단정하지 않습니다.
